Engineering

Tests that run offline in minutes, browser tests that drive the built app, a test that holds the project's own documents to its data, a sandbox and a public mode for a shared host, and a deployment that fits a free container.

Tests

The backend has {{backend_tests}} tests. All of them run offline, against the mock models and with no key, in about six minutes. They cover:

  • specification validation, including readable errors with paths, and code generation with its static safety check;
  • the verifier's statistics, and the repair loop with every planted fault, including the honest-failure path;
  • exact insights checked against Qiskit Aer (to 1e-8), Wootters concurrence against Qiskit, CHSH against brute force;
  • the optimiser's rewrite rules, fuzzed on random circuits; the challenge reference solutions reaching exactly par;
  • network physics and its sanity checks; orbits against Skyfield; solar position at the solstice; the J2 nodal drift;
  • chemistry against Szabo and Ostlund's tabulated values; QAOA and BB84 against Qiskit on the generated circuits;
  • the decoders' layouts, the exact matcher against PyMatching, and the stored precomputed results against a fresh computation;
  • the live adapters against recorded request shapes from Meta's documentation, and the API end to end.

pytest -m live makes one cheap real call per Meta model. It is skipped without a key, and cached after the first run.

Our own numbers, held to the app's rule

The app traces every number a model writes to the tool that computed it. The project applies the same rule to itself. tests/test_claims.py rebuilds every number that the README and the submission text quote from the data file it comes from: the hardware run, the referee, the learning curves, the codes, the whole paper, both decoders, the mission benchmark, the AI-alone benchmark, the ML verifier and the RSA-2048 comparison. It fails if a document quotes anything else, and it refuses a hardware number that comes from a rehearsal rather than a real device.

scripts/check_submission.py checks what the hackathon form needs: a public repository, video and demo links, the video's length, the thumbnail, test counts, quoted claims, no secrets in history, CI on the latest commit, and the deadline. Its first run caught the documents quoting 448 tests after the suite had grown to 468. This report is built the same way: scripts/build_report.py reads every benchmark number from data, and an unknown placeholder stops the build.

Continuous integration and browser tests

GitHub Actions runs three jobs on every push: the offline backend suite, the frontend type-check and build, and the end-to-end browser tests. The {{e2e_tests}} browser tests start the server on the offline models and drive the built app in Chromium. They check that every section shows its panels; that a sample sketch goes all the way to Verified; that the guided tour lands on every step and leaves a finished mission and discovery run; that the satellite planner flies a real satellite; and that no section scrolls sideways on a 390-pixel phone screen. The section list and tour steps are read from the app's own source, so the tests follow the app as it changes.

They caught a real bug. On a cold server, the tour scrolled to the decoder before the pulse lab above it had loaded. The pulse lab then grew and pushed the decoder 878 px down the page. The fix holds a panel in place for up to 15 s while the layout above it settles, and releases it the moment the visitor scrolls, clicks or types.

Security and public mode

  • Model-written code runs only after an AST check, in a separate Python process with a timeout and an environment scrubbed of keys, tokens and secrets. In public mode it is never executed at all: the agent runs Inkubit's own template code, and the planted-fault demo still works because the faults go into that code.
  • Costs on a shared host are capped at 300 billed model calls per UTC day, counted only on cache misses. After the cap, the labelled offline models answer.
  • Secrets. Before the repository was made ready to publish, every commit then in its history (78) was searched for key patterns (Meta, Hugging Face, GitHub, AWS, private keys) and for the literal Meta key. There were no hits in history, tracked files or the built frontend; .env was never committed. The deploy script never uploads .env.
  • A fresh clone, following the README exactly with a new virtual environment and no .env, starts in offline mode, every feature endpoint answers, and the test suite passes. The only skipped tests need the dev extras, Skyfield and Cirq.

Hosting on a free container

The Dockerfile builds the frontend with Node and serves everything from Python 3.13, as a non-root user, on port 7860. Hugging Face now requires a PRO account for Docker Spaces, so the free route is a container host's free tier, with 512 MB of memory and a tenth of a CPU, asleep when idle. Memory was measured in public mode:

MomentMemory in use
After start206 MB
After the labs and a mission223 MB
During a discovery run255 MB
Server plus sandbox at the peak of a sketch run385 MB

A tenth of a CPU makes heavy actions about ten times slower, and the start-up warm-up would have spent minutes of it after every wake. The input-free results (the observatory, the pulse sweep and its DRAG calibrations, 37 KB) are therefore stored with the app, and a test checks that they equal a fresh computation. Koyeb is preferred: it wakes in seconds and sleeps after an hour. A deploy link in the README fills in the repository, the Dockerfile, the port and the free instance.

The demo video, recorded by a script

scripts/record_demo.py drives the real app in headless Edge and records the browser's own screencast at 1920 × 1080 (H.264, via the ffmpeg bundled with imageio-ffmpeg), with caption cards and a visible cursor laid over the page. Its rules keep it honest. Every number in a caption is read from the recorded results, never typed in. Captions name a Meta model only when the server reports live Meta mode. Waits for the sandbox or for model calls are sped up 4× only with an on-screen tag. The current take runs 2:35, opens on the 3D scene and was recorded against the live models. A timed voice-over script sits beside it. The README's opening GIF and the video thumbnail are cut from the same recording.

Limitations and next steps

What Inkubit does not do, stated as plainly as what it does. Each limitation is also stated in the app or the README where it applies.

Limitations

  • Verification sees statistics. It cannot see a pure phase error that leaves the measured distribution unchanged, and it does not catch changes smaller than its threshold, such as an angle off by a few degrees. The optimiser's proofs, tomography and the Bell tests look further, but they are not run on every result.
  • Circuits. Feed-forward (mid-circuit measurement and gates conditioned on one measured bit) runs, verifies exactly and goes to IBM chips, but a measured qubit cannot be reused, and the tools built on a single state (step-through, live state, optimizer, proof sheet) refuse it. Circuits are capped at 12 qubits, 10 with feed-forward record qubits, and the noisy analyses at 10.
  • The sandbox is a guard rail, not an operating-system sandbox; on a shared host model code is not run.
  • The network model is analytic and simplified: simple BBPSSW purification, no multi-pair emission and lumped atmospheric loss. Its numbers are order-of-magnitude estimates, not engineering predictions. For the real satellites, pass times, elevations and clouds are real data, but key rates are estimates.
  • Noise. The decoders use phenomenological noise, not circuit-level noise. The generic noise preset is too pessimistic for a modern IBM chip; the calibrated preset uses median errors, not those of the patch a compiler picks. The H₂ lab's mitigation assumes the calibrated noise map is known.
  • Learned components carry their guarantees only for data like their training data: the ML verifier's interval held for {{ml_gal_cov}}% of textbook cases against {{ml_cov}}% on held-out ones. That is why exact checks still run.
  • Discovery and codes. "Fewest CNOTs found" is not a proof of minimality. The new biased-noise code's distances are proven, but its performance under a decoder has not been simulated.
  • Offline mode recognises only the three bundled sketches, and explains in English only.
  • Untested paths. The Muse Code CLI repair backend is opt-in and untested here, because the CLI was not installed. Meta's open-weight Glimmer model runs, but too slowly to drive the app, and no results from it are claimed.

Next steps

  1. Calibrate per patch. The median-calibrated preset already predicts the chip better than the generic one and than a digital twin did; per-qubit errors for the patch the compiler picks are the next step.
  2. Circuit-level noise for the decoders, so that Λ can be compared with hardware like for like, and a decoder study of the AI-designed biased-noise code.
  3. Qubit reuse after measurement (reset), for repeated syndrome extraction on top of the feed-forward that exists.
  4. Full-state tests on hardware: the discovered W and Dicke circuits tied in the computational basis; tomography would show what their fewer gates save in phase coherence.
  5. Multi-page lab notebooks: sketches that span pages, read as one experiment.

How the work was done

Every design decision was written down with its reason as it was made ({{n_decisions}} of them, Appendix B), including those that went against an easy claim: when the first AI-alone run showed the model exact on small circuits, the page said so and the test moved to bigger ones. Every feature that uses a model got an exact check, every quoted result came from a script that can be run again (Appendix C), and bugs found by tests are recorded with their fixes, because they show where a system like this can go wrong without anyone noticing.
