Sketch to verified code

The original pipeline: draw a circuit on paper, and get running code whose result is proven right by an independent simulation of what you meant. When the code is wrong, the agent explains why, fixes it and runs it again, live on screen.

The reading path. The user sees the photo and the specification side by side and can correct either.

A sketch can be a circuit or a quantum network; Muse Spark decides which from the photo. The result is not trusted blindly. It is a draft that the user sees overlaid on the photo: hovering over a box highlights its line in the editor, and the editor validates as the user types. Words and speech take a parallel path. Muse Spark fills the same draft schema from a description such as "Bernstein-Vazirani with secret 1011" or "300 km of fiber with 2 repeaters". Offline, a deterministic parser handles named algorithms, gate lists and simple networks, and anything else gets a list of what it understands, never a guess.

The specification

Everything downstream works from one JSON document, discriminated by kind and versioned. It is deliberately small: it is what the models fill, what the user edits, what the code is generated from, and what the verifier rebuilds the circuit from, independently.

{ "kind": "circuit", "version": "1.0", "num_qubits": 2, "num_clbits": 2,
  "operations": [
    {"gate": "H", "targets": [0], "source": {"bbox": [310, 250, 410, 350], "confidence": 0.97, "segment_id": "s0"}},
    {"gate": "CX", "controls": [0], "targets": [1]} ],
  "measurements": [{"qubit": 0, "clbit": 0}, {"qubit": 1, "clbit": 1}],
  "metadata": {"title": "Bell pair", "origin": "image"} }

The gate set (H, X, Y, Z, S, T and their inverses, √X, rotations, CX, CZ, controlled phase, SWAP and Toffoli) is enough for Grover search, Bernstein-Vazirani, Deutsch-Jozsa, the QFT, phase estimation, teleportation and the W state. Measurements are terminal, which keeps the independent prediction exact. A circuit without a measurement is invalid, because there would be nothing to verify. Unknown fields are errors, not silently ignored typos. Common aliases such as CNOT are normalised, because hand labels and model output use them. Networks list ground stations, satellites and repeaters with optional memory coherence times and apertures, and fiber or free-space links with lengths and losses.

Writing and running code safely

Muse Spark writes a standalone Qiskit script for the specification; offline, a deterministic template does. In demo mode, the first attempt is broken on purpose with one of six realistic bugs, so that the repair is always visible: a missing CNOT, a reversed CNOT, a wrong qubit index, a missing measurement, an old import path, or a faked result that prints plausible counts without running anything.

Model-written code is treated as untrusted. Before it runs, the abstract syntax tree is checked: only qiskit, qiskit_aer, json, math and numpy may be imported, and calls such as open, eval and exec are rejected. The script then runs in a fresh, isolated Python process in a scratch folder, with a 60-second timeout and an environment from which every variable named like a key, token or secret has been removed, so generated code can never read the Meta key. This is a guard rail, not an operating-system sandbox, and the README says so. On the public host, model-written code is never executed at all.

Verification

The verifier never reads the generated code. It rebuilds the circuit from the specification with its own builder and computes the exact, noise-aware distribution the run should produce: a density-matrix simulation with the preset's gate noise, then the readout error applied exactly to each bit. Then it compares that prediction with the counts the code actually produced. A run passes only if both of these hold:

TVD(measured, expected) ≤ max(floor, ³⁄₂ Σi √(pi(1 − pi) / N)) and Hellinger fidelity ≥ minimum

The second term is three standard deviations of sampling error on every outcome at once. For a Bell pair at 4,096 shots it is about 0.023, so honest runs essentially never fail. The floors (0.02, 0.03 and 0.04 for the ideal, low-noise and realistic presets) and the minimum fidelities (0.99, 0.985, 0.98) absorb the small differences between two independent constructions. Real faults are far outside these limits: a missing or reversed CNOT on a Bell pair gives a distance of about 0.46 to 0.5. In the submission's example, a correct Bell pair run was 0.004 from its prediction, against a limit of 0.040.

Known blind spots, stated in the app

Verification compares measurement statistics. It cannot see a pure phase error that leaves the outcome distribution unchanged, and it does not catch changes smaller than the threshold, such as an angle off by a few degrees. The circuit tools in Chapter 13 (state-by-state inspection, process-fidelity proofs, Bell tests and tomography) look further than the verifier does.

Diagnosis and repair

When a run fails, the agent explains why in plain words, from the statistics alone. Correlations that should exist but don't suggest a missing or reversed entangling gate. Wrong marginals suggest a gate on the wrong qubit. A single outcome where noise should spread the counts suggests faked results. For example:

"Attempt 1 failed: expected ~50% |00⟩ and 50% |11⟩, got 49% |00⟩ and 48% |01⟩. Bits c0 and c1 should agree every time but come out independent; the entangling gate looks missing or points the wrong way. Repairing…"

The repairer (Muse Spark live, a deliberately limited rule-based repairer offline) gets the full evidence: the specification, the code, the error, the verifier's verdict, the diagnosis and the history of earlier attempts. Every attempt keeps its code and a unified diff, so the interface shows exactly what each repair changed. There are at most four attempts. If the repairer returns identical code, the loop stops and reports failure instead of burning attempts. A run that cannot be fixed is reported as Not verified, and its code and counts are labelled as unverified.

The planted-fault benchmark

scripts/benchmark.py runs every gallery circuit under realistic noise, once clean and once with each fault that can be planted in it. It runs offline (template code and the rule-based repairer), so it measures the agent loop and the independent verifier, not a language model. 55 of 55 runs ended correctly: every clean run verified on the first attempt, all 37 repairable faults were verified after one repair, and all 9 faked results were caught. The rule-based repairer deliberately has no rule for faked results, which is how the honest-failure path is demonstrated and tested. Muse Spark gets the same evidence and can fix that fault too.

Understanding the result

A verified result is only the start. Muse Spark explains it to a student using the real numbers, in any of twelve languages, each in its own script; offline, an English template is used and the page says so. Muse Image draws a clean diagram beside the exact one. The user can then ask questions about the run ("why did attempt 1 fail?"). Muse Spark answers only from that run's facts and says when the facts don't contain the answer. Any design can be shared as a link that carries the whole specification in the URL, so nothing is stored on a server, or downloaded as a one-file HTML report.

Mission control

One request, typed, spoken or photographed, becomes a plan of exact tools that runs live in parallel, repairs itself, verifies every step and writes a report in which every number is traced.

From one request to a plan

A mission can combine words, a photo and speech: "connect two cities 1,200 km apart with quantum-secure keys, compare satellite and fiber, and check whether a spy on 25% of the photons is caught". A photo goes through the sketch pipeline (SAM 3.1 and Muse Spark into a validated specification). If it is not a drawing, it goes to the Rosetta's notation reader instead. Muse Spark, or Muse Wonder in deep mode, then plans up to eight steps under a JSON schema. Each step has a tool, arguments (checked against that tool's own schema), dependencies and a stated purpose.

Circuits pass between steps by reference: an argument circuit_from names an earlier step, or the photo. A proven shorter circuit from the optimiser can therefore feed the ML verifier without the model copying gates, which is where models make transcription mistakes.

Running in parallel

Before anything runs, the plan is checked: unknown tools are dropped, and every dependency must point to an earlier step, which rules out cycles. A thread pool then runs every step whose dependencies are done. Each change is an event that streams to the browser and lights up the graph. A step that fails gets one repair: Muse Spark sees the error and the tool's schema and returns new arguments. Live runs in the interface took 12 to 23 seconds for missions such as two cities, photo to hardware, a molecule at three bond lengths, RSA, and exam scheduling.

Verification that does not trust the tools

The tools are exact, but the checks assume they could still be wrong, through a bug or arguments a model chose badly. Every tool has physics invariants:

  • the variational principle for H₂: no computed energy below the exact ground state;
  • QAOA never above the brute-force best cut;
  • Shor's factors must multiply back to the number;
  • link fidelity in [¼, 1], and no key above the 11% error rate;
  • for circuits, two independent noisy simulators that must agree to 1e-6: Inkubit's closed-form channels and Qiskit Aer's density matrix.

The ML verifier (Chapter 15) also runs on every circuit. A miss there grades the model, not the result, so it appears as a note and never flags the step.

Reports with every number traced

Muse Spark writes the report from the step facts and the text of their checks. The tracer then matches every number in the report against the tool results at the precision written. A number counts as traced only if a tool computed it; rounding 2,089 to 2,090 is not traced, by design. A finished mission downloads as one self-contained page: the plan, every step with its results, checks and arguments, the report with each number marked green (traced) or amber (not traced), the model calls, and standalone Qiskit code for every circuit.
