Architecture

A Python backend of exact engines behind a FastAPI server, a React app that streams every step live, and a model layer through which every Meta model call passes. That layer has an offline twin, a cache and an honest fallback.

Overview

Q-Canvas is a single web application. The browser sends a request: a photo, a spec, a mission, a question or a paper. The server starts a job and returns at once. The job's events (plan, step started, attempt failed, repaired, verified) stream back over server-sent events, so the user watches the work happen instead of waiting for a result. There is no database: jobs live in memory, share links carry the whole spec in the URL, and per-viewer progress such as challenge stars is kept in the browser.

The model layer and the exact engines never call each other directly. Orchestration code such as the agent loop, mission control or a lab's driver asks the model for a proposal, hands it to an engine and passes the result through the checks. That separation is why the model can be swapped for an offline mock without changing anything downstream.

The frontend

The app is React 19 with TypeScript, built by Vite, about {{ts_lines}} lines in {{components}} components. The start page leads with mission control, and a switch puts the quick assistant in the same place. Everything else sits in five sections that mount only when opened, so heavy requests do not start on page load. The open section is kept in the URL.

Visual rules are simple and kept everywhere. The colours are a charcoal ground, one blue for measured data, one orange for predictions, green and red only for pass and fail, and gold reserved for entanglement. The Bloch spheres are drawn in 3D as SVG and share one camera. Every chart has a crosshair readout, a legend and a "Show the numbers" table, and motion stops under prefers-reduced-motion. A guided tour (/#tour) walks through the highlights in under two minutes. It starts a real mission and a real discovery run early and comes back to their results.

The model layer

Every model job (read a sketch, write code, repair it, explain, plan a mission, propose layouts) is an interface with two implementations. The Meta implementation calls https://api.meta.ai/v1 using only the endpoints and fields in Meta's documentation; the pages used are listed in the repository. The mock implementation is deterministic and offline. It recognises the bundled sample sketches by file hash and returns their recorded readings. It writes code from the template, repairs with a rule-based repairer, explains from templates filled with the real numbers, and refuses anything it can't do honestly.

  • Cache. Responses are cached on disk by request hash, so repeated demos and runs cost nothing and are reproducible.
  • Fallback. With QCANVAS_ALLOW_FALLBACK=1, a failed live call is answered by the mock, and the badge says Mock fallback together with the error.
  • Public mode. With QCANVAS_PUBLIC=1 on a shared host, code written by a model is never executed (the agent runs Q-Canvas's own template code). Billed calls stop at 300 per day, counted only on cache misses, after which the labelled offline models answer.

Jobs, events and streaming

Long work runs as a job with an event bus. Each step (a plan, an attempt, a verdict, a diagnosis, a repair, a tool result, a check) is a plain-language event that streams to the browser as a server-sent event. Mission control runs independent steps on a thread pool; each change is an event, and the browser draws it on a live graph. Slow results that need no input, such as the observatory's simulations and the pulse lab's sweep and DRAG calibration, are computed once and stored with the app. A test checks that they equal a fresh computation, so a cold start on a small container does not spend minutes recomputing them.

Muse Spark is the default for nearly everything: it is fast, reads images, follows schemas and calls tools. Muse Wonder is Meta's most capable model, built for multi-step agentic work. It costs four to five times as much per token, so it is used only where depth pays: long tool chains, the whole-paper pass and the referee. Standard-mode model IDs are used, so judges' and users' content is not used for training.

Structured output as the contract

Every model step that feeds an exact engine uses structured output: a JSON schema in response_format that the answer must satisfy. The schemas are kept flat on purpose, with every field required and no tuples or optional objects, because that is the most reliable shape for constrained decoding. A draft is converted into a real specification and validated. If validation fails, the model is re-prompted once with the readable errors, for example operations[2] (RX): target qubit 3 is out of range; this circuit has 2 qubits.

The first live run, with fallback switched off so that nothing could hide behind the mock, found two problems that offline tests could not. The circuit draft schema allowed MEASURE as a gate but had no field for its classical bit. Muse Spark put the GHZ sketch's meters there, so the spec could never validate; the schema and prompt were fixed. Hindi explanations came back in Latin letters; the prompt now names each language's script. The whole live run cost about $0.40.

Tool calling and number tracing

The assistant, Ask Q-Canvas, is Muse Spark with tool calling. It chooses among nine function tools, each a thin wrapper over an exact engine: circuit simulation, the optimiser, the H₂ molecule, BB84, QAOA, Shor's algorithm, network links, error correction and the Rosetta. It calls several in parallel when it needs several. The system prompt forbids working out a quantum result without a tool. Tool errors go back to the model as data, so it can fix its own arguments.

After the answer, every number in it is matched against the numbers in the tool results and in the question, at the precision written or as a percentage. Small counts and bitstrings are skipped. The page shows "n of n traced", or lists the numbers that were not traced. The first live answers traced completely: 3 of 3, 5 of 5 and 14 of 14. Muse Wonder's deep mode answered "plan a 1,200 km satellite key link, then check whether a spy on 20% of the photons would be caught" by calling the link planner and BB84 in parallel, in 8.9 s, with 13 of 13 numbers traced. Mission control applies the same tracer to its reports (Chapter 6).

Seeing: SAM 3.1 and set-of-marks prompting

Reading a sketch pairs the two models the way Meta's documentation recommends: Muse Spark interprets the scene and decides what to segment, then hands the concepts to SAM. Muse Spark looks at the photo and names one to four noun phrases ("box with letter", "filled dot", "circle with plus"). SAM 3.1 runs once per phrase with confidences switched on, and its token output is parsed into boxes scaled to the uploaded image. Muse Spark then sees the photo, a copy with numbered boxes drawn on it and the box list, and fills the draft schema, linking every operation to the box it came from.

SAM is trained on photographs, and pen strokes on paper sometimes give few or no masks. The draft schema therefore also asks Muse Spark for each element's own box on its 0–1000 grid. If an element has no SAM segment, Muse Spark's box is used at confidence 0.6 and labelled seen by muse-spark-1.3 in the overlay. The overlay is never empty, and it never claims SAM found something it did not.

Voice and images

"Say it" records the microphone with Web Audio, downsamples to 16 kHz and encodes a mono 16-bit WAV in the browser, so the server needs no ffmpeg. The recording goes to Muse Voice Transcribe in push-to-talk mode with a keyword list (qubit, Hadamard, CNOT, GHZ, Shor, …) that biases recognition toward quantum words. In a live check, three synthesised clips played through a fake microphone were transcribed in 3 to 4 s and became the right GHZ, Shor and satellite specifications. Offline, the button uses the browser's own recogniser, and the server never invents a transcript.

Muse Image draws a clean illustration of the final design. It is always shown next to the exact Qiskit drawing, so an imperfect picture can never mislead. The nine use-case images were generated in one restrained style (dark charcoal, off-white lines, one gold accent, no text) by a cached script, at about one cent per image.

Reliability and cost

  • Truncated answers. A cut-off JSON answer is a successful HTTP response, and the cache stores it. The retry therefore doubles the token budget and marks itself, which changes the request, while the first attempt stays identical and keeps its cache entry.
  • Documents. PDFs go to the model as a file block with a base64 data URL. For a long paper, pypdf cuts out only the pages each experiment needs (Chapter 9).
  • Cost control. Everything is cached by request hash. Public mode caps billed calls per day. Muse Wonder is opt-in except where its depth is the point.

An open-weight model on a laptop

Meta's open-weight models were tried too. Muse Spark Open is an 816-billion-parameter mixture of experts, out of reach of an 8 GB laptop GPU. Muse Glimmer (27.9B, 4-bit, 18 GB with its vision projector) runs through Ollama's OpenAI-compatible endpoint with the same Meta client; only the base URL, the model name and a timeout change. It ran split 71% on the CPU and 29% on the GPU at about 1.6 tokens a second, so a reasoned answer took about five minutes. It answered the Bell pair exactly, under the JSON schema. That is too slow to drive the app, so the hosted models stay. A full AI-alone benchmark on Glimmer was stopped after one circuit when the machine ran low on memory, so no Glimmer results are claimed.
